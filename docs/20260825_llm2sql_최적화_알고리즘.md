# txt2sql 최적화 알고리즘

**작성일:** 2026-08-25  
**대상 코드:** `contract-capability-sqp-20260825`  
**근거:** `32_post_fix500` vs `34_full500`, Query Contract / Capability / SQP 구현,  
「국내외 고성능 Text-to-SQL 알고리즘 검토 및 llm2sql 적용 최적화 방안」 적합성 평가

이 문서는 논문 검토서가 아니다. **지금 파이프라인에 넣을 목표 알고리즘**이다.  
검토서가 제시한 계층 분리와 금지 목록은 유지하고, **적용 형태와 순서만 닫힌 KorDB·현재 실패 분포에 맞게 고친다.**

---

## 1. 한 줄 정의

> **닫힌 스키마에서, 질문을 typed Query Contract로 고정한 뒤  
> 필드 단위로 완전히 지원하는 최저비용 경로만 실행하고,  
> SQL이 아니라 Plan과 실행 결과 shape로 검증하는 Text-to-SQL.**

이름: **Field-Covered Contract Pipeline**  
검토서의 *Contract-Aware Adaptive Hybrid Text-to-SQL*과 같은 계층을 쓰되,  
LitE-SQL 벡터 검색·DIN-SQL 4단 LLM·상시 다중 후보는 **주경로가 아니다.**

```text
Normalize
  → Bind (닫힌 카탈로그: dataset / field / value)
  → Query Contract (Source of Truth)
  → Capability.covers(contract)          # 필드 단위, family 단위 아님
       ├─ 완전 지원 → 최저비용 Router → execute
       └─ 미지원   → SQP (연산자 완전) → compile
  → verify(contract, plan)
  → execute
  → verify_result(contract, rows)        # 지금 없음
       └─ 실패 시에만 replan / 제한적 resample
```

후속 질문은 직전 SQL 재사용이 아니라 **Contract Δ 병합 후 같은 파이프라인**이다.

## 2. 왜 이 형태인가

### 2.1 이미 끝난 것

Contract-first 전환은 production에 들어갔다.

| 불변식 | 상태 |
|---|---|
| Query Contract가 모든 라우트 결정보다 앞선다 | 구현됨 (`run_ask` → `extract_contract`) |
| Router는 완전 지원일 때만 실행 | 골격만 (`legacy_route_eligible`) |
| 전 질문을 SQP/LLM SQL로 보내지 않는다 | 유지. 단순 건수 9/9 |
| Compiler는 Plan만 SQL로 직렬화 | 유지 |

### 2.2 점수가 말해 주는 병목

| 지표 | 3-core (`32`) | contract-first (`34`) |
|---|---|---|
| full-500 | 393/500 **78.6%** | 367/500 **73.4%** (−26) |
| Q3_agg_rank 24 | 10/24 | 10/24 (변동 없음) |
| legacy hit / 정확도 | 88 / **88.6%** | 136 / **75.7%** |
| SQP hit / 정확도 | 346 / 83.5% | 292 / 82.2% |
| RANGE_BOUND_DROPPED | 9 | 17 |
| count kind Δ | — | **−21** |
| 공간복합 Δ | — | **−8** |
| 후속 Δ | — | **−4** |

해석:

- 분기는 성공했다. 단순 건수는 Router에 남고, 전체를 SQP로 몰지 않았다.
- 하락은 **거짓 eligible Router**다. `THRESHOLD_COUNT` / `D010` / `D198`이 면적·연도만 먹고 구조·용도·공간 조건을 버린 채 실행됐다. 대표 회귀 쌍: `semantic_plan_count → building_area_threshold_count` (6).
- Q3 정체는 라우팅이 아니다. SQP가 ratio / percentile / derived를 못 채우면 `semantic_plan_clarify`로 죽는다.
- ENTITY 48건의 상당수는 BIRD식 컬럼 검색이 아니라 **데이터셋 선택(D010 vs D198 vs BAS)과 건물명 값 연결**이다.

따라서 최적화 단위는 문항 패치가 아니라 아래 다섯 계층이다.

1. Capability를 **필드 커버**로 승격  
2. 닫힌 카탈로그 **Bind**를 Contract 입력으로  
3. SQP **연산자 완전성** (Q3 포함)  
4. **실행 결과 shape** 검증  
5. 후속을 **Contract Δ**로 병합

## 3. 설계 불변식

다음을 깨는 변경은 최적화가 아니다.

```text
I1. Query Contract = 사용자 요구의 유일한 Source of Truth
I2. Capability.covers(C) = C의 모든 슬롯을 그 경로가 구현한다
I3. Partial coverage must never execute a deterministic route
I4. 후보가 여럿이면 첫 매치가 아니라 최저비용 완전커버 경로
I5. Compiler는 Plan만 직렬화한다. LLM → SQL은 주경로가 아니다
I6. 실행 결과가 Contract.query_kind와 맞지 않으면 그 SQL은 오답이다
I7. 후속 = 직전 Contract ⊕ Δ. 직전 SQL 재사용은 금지
I8. QID·골드 SQL·문항 키워드 예외 분기는 금지
```

금지 (검토서 §27 + 평가 반영):

- CHESS / CHASE 전 질문 multi-agent
- XiYan식 상시 다중 생성기
- 질문 → LLM → SQL 회귀
- Router 전면 제거, 병렬 라우팅 프레임워크 신설
- QID 하드코딩, `"구조별" in q` 같은 키워드만으로 defer
- BIRD 70% 숫자를 llm2sql 목표로 사용

## 4. 대상 도메인 가정

llm2sql은 cross-domain BIRD가 아니다.

| 가정 | 함의 |
|---|---|
| 스키마가 닫혀 있다 | 건물(D010), 행정, 기초구역(BAS), 산업단지, D198 |
| 조인 그래프가 작다 | 공간 관계(교차, 버퍼, 단지 내부)를 경로 표로 둘 수 있다 |
| 값 연결이 핵심이다 | `엘시티` → 대장 공식명칭, 법정동 vs 행정동 |
| deterministic Fast Path가 자산이다 | 단순 건수·임계값·순위는 Router가 더 빠르고 정확하다 |

그래서 LitE-SQL의 **벡터 컬럼 검색을 즉시 적용하지 않는다.**  
스키마 링크는 카탈로그 lookup + alias + (필요 시) 값 검색이다.

## 5. 파이프라인

```text
ask(question, session)
        │
        ▼
 ① Normalize
        │  표기 정규화, 단위(㎡/m), 세션 rewrite(표면형만)
        ▼
 ② Bind                         ← 지금 거의 없음. Contract 앞단
        │  dataset / field / value / spatial_path
        ▼
 ③ extract_contract             ← 있음. 슬롯을 Bind 결과로 채워야 함
        │  QueryContract
        ▼
 ④ session_merge (후속이면)     ← 직전 Contract ⊕ Δ
        │
        ▼
 ⑤ is_sufficient?               ← coverage
        │  no → clarify 또는 unresolved LLM (슬롯만)
        ▼
 ⑥ detect_route_candidates      ← 실행이 아니라 후보
        │
        ▼
 ⑦ field_covers(route, C)       ← 지금 family gate. 필드 커버로 교체
        │
        ├─ eligible 있음 → argmin cost(eligible) → Router → SQL
        │
        └─ 없음 → generate_semantic_plan(C)
                      │
                      ├─ unresolved → 구조 예제 + 슬롯 LLM
                      ▼
                   verify(C, plan)
                      ▼
                   compile(plan) → SQL
        ▼
 ⑧ execute_readonly
        ▼
 ⑨ verify_result(C, rows)       ← 지금 없음
        │  ok → return
        └─ fail → replan_once | adaptive_resample (저신뢰만)
```

코드 대응:

| 단계 | 현재 함수 | 목표 |
|---|---|---|
| ① | `run_ask` session rewrite | 유지. SQL 재사용 금지 |
| ② | 없음 | `bind_catalog(question) → Binding` |
| ③ | `extract_contract` | Binding을 슬롯에 기록. 구조·용도·시간·공간을 predicate로 |
| ④ | list-attr / year-grain 직전 SQL | `merge_contract(prev, delta)` |
| ⑤ | `QueryContract.is_sufficient` | Bind confidence 포함 |
| ⑥ | `detect_route_candidates` / `try_route` | 유지 (후보만) |
| ⑦ | `legacy_route_eligible` | `supported_fields`가 구조·용도를 빼지 않게 |
| SQP | `generate_semantic_plan` + `verify_contract` | ratio/percentile/divide/bins를 항상 생성 |
| ⑧ | 기존 실행 | 유지 |
| ⑨ | 없음 | `verify_result` |

## 6. 단계 명세

### 6.1 Bind — 닫힌 카탈로그 연결

**입력:** 정규화된 질문  
**출력:** `Binding`

```text
Binding
  datasets:     [{id, confidence}]     # d010, d198, bas, admin, industrial
  fields:       [{mention, field, confidence}]
  values:       [{mention, column, resolved, confidence}]
  spatial_path: {op, left_entity, right_entity} | None
  aliases:      법정동/행정동, 건물명 공식명칭
```

규칙:

1. 기본 엔티티는 건물(D010). D198 전용 속성(사용승인연도 등)이 있으면 D198을 주 데이터셋으로 올린다.
2. 기초구역·산업단지·행정동 교차가 있으면 `spatial_path`를 채우고, 임의 `ST_*`를 만들지 않는다.
3. 건물명은 exact → alias 사전 → (필요 시) `A24`/`A25` 값 검색. 벡터 컬럼 검색이 아니다.
4. confidence < τ 인 슬롯은 Contract `unresolved_spans`로 넘긴다. 추측으로 채우지 않는다.

검토서 A1(LitE-SQL 벡터)의 **llm2sql 이식 형태**는 이 Bind다.  
컬럼 임베딩 인덱스는 catalog가 커지기 전까지 넣지 않는다.

### 6.2 Query Contract — 분해 결과

DIN-SQL의 가치는 4단 LLM이 아니라 **슬롯이 Source of Truth**라는 점이다.  
`extract_contract`가 그 계층이다. LLM 분류기를 앞에 두지 않는다.

필수 슬롯:

```text
places, datasets
predicates[]     field, op, value, negated
boolean_ops      and / or / not
aggregations     count | sum | avg | min | max | median | stddev | percentile
groups
outputs
order, limit
ratios[]         numerator, denominator, as_percent
derived_metrics[]  typed divide (연면적/대지면적 등)
spatial          wants_spatial, spatial_path
temporal         wants_temporal, year_range | age_years
query_kind       count | list | rank | group | scalar | ratio | compare | meta
```

지금 구멍: 구조·용도·위반건축이 span으로만 남고, threshold capability의 `pred_fields`에서 빠져 **거짓 eligible**이 된다.

채움 규칙:

- 「일반철골」「벽돌구조」「블록구조」「목구조」 → predicate `structure`
- 「공동주택」「단독주택」「공장」 → predicate `usage`
- 「위반건축」 → predicate `violation` / D010 `A20`
- 「지어진지 N년」 → temporal + 사용승인 환산
- 「지하」 → `wants_basement` (이미 있음)
- 「비율」「몇 퍼센트」「상위 p%」 → ratios / percentile. 버리지 말 것

`is_sufficient()`는 문법 coverage만이 아니라 **Bind된 field가 predicate로 닫혔는지**를 본다.

### 6.3 Capability — 필드 커버

현재 `RouteCapability`는 family 플래그다. `THRESHOLD_COUNT`는 `between + count`만 본다.  
「경량철골이고 연면적 1500㎡ 이상」이면 면적만 먹고 실행된다 (`Q136` 등).

**covers 정의:**

```text
covers(R, C) ⇔
    C.is_sufficient()
    ∧ C.query_kind ∈ R.kinds
    ∧ C.datasets ⊆ R.datasets
    ∧ pred_fields(C) ⊆ R.supported_fields
    ∧ 모든 agg/group/ratio/spatial/temporal/basement 플래그가 R에 있음
    ∧ OR/NOT/다중 predicate를 R이 지원
```

`supported_fields`에서 `usage`, `structure`, `violation`을 빼지 말 것.  
그 필드가 있는 라우트만 해당 predicate를 허용한다.

최저비용 순서 (완전 커버인 것만):

```text
legacy_simple_count
  < building_threshold_count | list
  < building_rank | usage | profile | name_lookup
  < d010_attr_* | d198_* | bas_* | industrial
  < spatial_*
  < semantic_plan
```

후보 루프는 **첫 성공이 아니라 이 순서로 완전 커버를 고른다.**  
어느 라우트도 커버하지 못하면 SQP다.

기대 효과: legacy 정확도 75.7% → 32 수준(약 88%) 복원, RANGE_BOUND 17 → 9 부근, count −21의 상당 부분 회수. **full-500 78.6% 복원이 이 한 계층의 목표다.**

### 6.4 Router Fast Path

완전 커버인 질문만 탄다.

허용 예:

- 해운대구 건물 몇 채야 → `legacy_simple_count`
- 연면적 1000㎡ 이상 채수 (다른 속성 없음) → `building_area_threshold_count`
- 높이 상위 N → `building_rank`

거부 예 (지금 실행되고 있어 깨짐):

- 공장·경량철골 + 연면적 임계값 → threshold 거부, SQP
- 사용승인 연도 + 건축면적 + 용도 → D198 단독 count 거부
- 산업단지 안 + 연면적 → threshold 거부, 공간 경로 또는 SQP

Router SQL도 ⑨ `verify_result`를 통과해야 한다.

### 6.5 Semantic Query Plan — 연산자 완전성

SQP는 “Router가 못 하면 보내는 곳”이 아니라 **복합 Contract의 표준 경로**다.  
Q3 14실패의 다수가 `semantic_plan_clarify`인 이유는 문을 잘못 열어서가 아니라, Plan이 의미를 버려 verifier가 거절하기 때문이다.

필수 연산자 (휴리스틱이 항상 생성):

| Contract | Plan 노드 |
|---|---|
| ratio + denominator | `agg_filter / agg_base` 또는 조건부 COUNT, 백분율 출력 |
| percentile | `percentile_cont` / 윈도 |
| derived divide | typed `expr` (연면적/대지면적). 문자열 나눗셈 금지 |
| fixed bins | `width_bucket` / CASE bin |
| group_rank | GROUP BY + ORDER + LIMIT |
| spatial_path | 카탈로그의 조인 경로만 |
| NOT / OR | predicate tree. 드롭 금지 |

`verify_contract`는 유지하되, **실패 시 슬롯을 지우고 clarify하지 않는다.**  
부족한 연산자를 채운 뒤 한 번 더 generate한다. 그래도 안 되면 unresolved LLM (슬롯만).

PICARD식 SQL 토큰 제약은 쓰지 않는다. 제약은 **Plan JSON 스키마**에 둔다.

### 6.6 Compiler

`compile_semantic_plan(plan) → SQL`  
Plan에 없는 절을 컴파일러가 추론하지 않는다.  
공간 함수는 `spatial_path`에 있는 `ST_Intersects` / `ST_Within` / `ST_DWithin`만.

### 6.7 Execution Result Verification

LitE-SQL / VET / ReEx-SQL의 llm2sql 최소 이식.  
전 질문 중간 SQL 트레이스는 넣지 않는다 (p95 이미 13–14s).

```text
verify_result(C, rows):
  count  → 행 1, 정수 1. 다중 숫자·빈 리스트는 실패
  ratio  → [0, 100] 또는 비율 행. 건수 스칼라만 있으면 실패
  rank   → 행 수 ≤ limit, order 필드 존재
  list   → 요청 output_fields 존재
  group  → group 키 + 집계값
  spatial count → 단일 정수. engine-fail 메시지는 실패
```

실패 시:

1. 같은 Contract로 SQP 재생성 1회 (Router 오답이면 경로 전환)
2. 그래도 실패이고 `unresolved` 또는 confidence 낮으면 ⑪
3. 그 외는 오답으로 반환. 침묵하고 잘못된 숫자를 보여 주지 말 것

기대 효과: count-mismatch를 채점 전에 차단. 34에서 늘어난 오답 Router SQL을 사용자/평가에 넘기지 않음.

### 6.8 Follow-up = Contract Δ

후속 93건: 55.9% → 51.6%.  
원인은 직전 SQL을 붙이거나, 새 질문을 빈 Contract로 다시 뽑아 list 라우트로 새는 것이다.

```text
C_t = merge(C_{t-1}, extract_contract(q_t), Bind(q_t))
  - 「그중」「그 건물」 → entity/place 유지
  - 새 필터·연도·용도 → predicate 추가
  - query_kind가 바뀌면 (목록 → 건수) kind만 교체, 필터는 유지
그다음 ⑤부터 동일
```

list-attr / year-grain의 “직전 SQL 재사용”은 이 병합으로 대체한다.

### 6.9 Spatial path graph

공간복합 −8, 순수 공간 −3.  
임의 공간 SQL이 아니라 **허용 경로 표**다.

```text
building ⋈ admin     (법정동/시군구)
building ⋈ bas       ST_Intersects
admin    ⋈ bas       ST_Intersects
building ⋈ industrial ST_Within
point    ⋈ building  ST_DWithin(buffer_m)
```

`Binding.spatial_path`가 이 표에 없으면 SQP도 해당 조인을 만들지 못하고 unresolved다.  
이것이 DCG-SQL 그래프의 닫힌 스키마 버전이다.

### 6.10 Unresolved-only LLM과 예제

주경로가 아니다.

호출 조건 (모두 충족):

- Contract에 unresolved 슬롯이 있다 **또는** verify_result 1회 실패
- Router/휴리스틱 SQP가 그 슬롯을 구현하지 못한다

입력: Contract JSON + 해당 슬롯 + **Contract signature 유사 예제 소수**.  
출력: SQL이 아니라 **슬롯 채움 또는 Plan 노드**. Compiler가 SQL을 만든다.

DAIL-SQL few-shot은 이 호출이 생긴 뒤에만 효과가 있다. 지금 휴리스틱이 대부분인 상태에서는 넣지 않는다.

### 6.11 Adaptive resample

저신뢰·검증 실패만. K는 작게 (2–3).  
후보마다 ⑨를 통과한 것만 고른다.  
검증 없이 재생성하면 오답 Router SQL을 여러 개 뽑을 뿐이다. **⑨ 다음 단계.**

RL (ReEx-SQL, ReSQL)은 미룬다.

---

## 7. 의사코드

```python
def solve(question, session):
    q = normalize(question)
    binding = bind_catalog(q)                          # ② 닫힌 스키마

    contract = extract_contract(q, binding)            # ③
    if session.has_prev_contract:
        contract = merge_contract(session.prev, contract, binding)  # ④

    if not contract.is_sufficient() and not contract.unresolved_spans:
        return clarify(contract)

    eligible = [
        r for r in detect_route_candidates(q, contract)
        if field_covers(r, contract)                   # ⑦ 필드 단위
    ]

    if eligible:
        route = min(eligible, key=route_cost)
        rows = execute(compile_route(route, contract))
        check = verify_result(contract, rows)          # ⑨
        if check.ok:
            return rows
        # Router 오답 → SQP로 강등
    else:
        check = Fail("no_eligible_route")

    plan = generate_semantic_plan(contract)            # 연산자 완전
    if plan.unresolved:
        plan = fill_unresolved(contract, plan)         # ⑩ 슬롯 LLM, 선택

    verify_contract(contract, plan)                    # 실패면 재생성 1회, clarify로 슬롯 삭제 금지
    rows = execute(compile_semantic_plan(plan))
    check = verify_result(contract, rows)

    if check.ok:
        return rows
    if should_resample(contract, check):               # ⑪ 저신뢰만
        return select_verified(resample(contract), contract)
    return fail(check)
```

## 9. 구현 단계와 기대 효과

골드 QID를 코드에 넣지 않는다. 회귀는 카테고리·kind·경로 정확도로 본다.

### Phase 1 — 거짓 eligible 제거 (S, 작음)

- `pred_fields`에 structure / usage / violation / temporal / spatial을 포함
- `THRESHOLD_*`, `d010_attr_*`, `d198_*`, `bas_area_*`의 `supported_fields`를 실제 구현과 일치
- 후보 중 최저비용 완전커버만 실행

**성공 기준:** legacy 경로 정확도 ≥ 85%, RANGE_BOUND ≤ 10, full-500 ≥ 78%, 단순 건수 9/9 유지, pytest Cases A–F 유지.

### Phase 2 — 실행 shape 검증 (S, 작음)

- `query_kind`를 Contract에 명시
- `verify_result` 후 Router 실패 시 SQP 1회

**성공 기준:** count-mismatch가 채점 결과로 새지 않음. p50 급증 없음 (재시도는 실패 건만).

### Phase 3 — SQP 연산자 (S, Q3)

- ratio denominator, percentile, typed divide, fixed bins를 clarify 없이 생성
- verifier 실패 → 슬롯 삭제 금지

**성공 기준:** Q3_agg_rank > 10/24, 집계비율 카테고리 상승, clarify 47 감소.

### Phase 4 — 후속 Δ (S)

- `merge_contract`, 직전 SQL 재사용 제거

**성공 기준:** 후속 카테고리 ≥ 32 수준 (55.9%).

### Phase 5 — Bind + 공간 경로 (S/A)

- 데이터셋 선택, 건물명 alias, spatial_path 표

**성공 기준:** ENTITY 감소, 공간복합 ≥ 32 수준 (88.6%).

### Phase 6 — LLM·예제·resample (A)

Phase 1–5 이후에도 unresolved인 질문만.

## 10. 오류 위치

유지보수 단위. 한 실패를 여러 계층에 패치하지 않는다.

```text
Bind Error              잘못된 dataset / 건물명 / 동 종류
Contract Error          슬롯 누락 (구조·비율·시간)
Capability Error        거짓 eligible 또는 과잉 defer
Plan Error              연산자 미생성, 조인 경로 없음
Compiler Error          Plan과 다른 SQL
Execution Verify Error  shape 불일치 (여기까지 오면 SQL은 이미 의심)
Followup Merge Error    Δ 미적용
```

## 11. 성공 판정 (알고리즘 관점)

부분 키워드 패치가 아니라 아래가 동시에 성립해야 이 알고리즘이 동작하는 것이다.

1. 단순 건수는 Router, 복합 속성은 SQP. 부분 라우트 실행 0.
2. full-500이 최소 32 수준(78.6%)을 회복하고, Q3는 라우팅이 아니라 Plan 연산자로 오른다.
3. count 질문이 다중 숫자·빈 리스트를 정답처럼 반환하지 않는다.
4. 후속이 직전 필터를 유지한다.
5. LLM 호출 수는 unresolved·검증 실패에만 비례한다.

BIRD/Spider 점수는 이 판정에 쓰지 않는다.
